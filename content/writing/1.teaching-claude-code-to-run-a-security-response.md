Security release day at an agency has a particular shape. The advisory lands, and the first question is simple: are we affected? Answering it isn't. At [Happy Dog](https://happydog.digital) that question covers more than forty production applications, spread across a Kubernetes cluster, shared cPanel servers, a few single-purpose VPSes, PaaS platforms, managed WordPress hosting, static sites, and mobile apps. PHP is the biggest share, but there are plenty of Nuxt apps and a few Go and Python services alongside it, and each combination gets its updates through a different channel: a distro or vendor package repository, a Docker base image, a platform that manages the runtime for us, or a lockfile we bump ourselves.

This month I turned that response into a Claude Code [skill](https://code.claude.com/docs/en/skills), and we've now run it twice: once to validate our rollout for the PHP remote code execution advisories, and today for a set of Symfony security releases. This post covers how it's built and what the two runs taught it.

## Where this started

On October 21, PHP [published fixes](https://www.php.net/archive/2026.php) for two critical bugs in multipart request handling ([CVE-2026-109618](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w) and [CVE-2026-109619](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp), both CVSS 9.2), after an embargo break the day before. We worked that response with Claude Code, and it went well, with one exception: at one point a session changed a live edge security policy without asking first. Nothing broke. That isn't the point. An agent that can read everything is enormously useful during an incident. An agent that decides on its own to change production during an incident is a second incident.

So once the dust settled, I wrote the process down as a skill, with that rule as its center.

## The shape of the skill

A Claude Code skill is a directory with a `SKILL.md` and whatever supporting files it needs. This one has an estate inventory, four briefs for [subagents](https://code.claude.com/docs/en/sub-agents), a report template, and a guard hook. The main session acts as the orchestrator: it doesn't do the investigating, it hands that out, merges what comes back, holds every approval, and owns the commits.

Every response starts the same way. The orchestrator gets an ID and a workspace in my home directory, deliberately outside every repository, because a map of what's exposed where doesn't belong in version control. Then the orchestrator reads the advisory itself and writes a single `advisory.md`: affected and fixed versions per branch, the vector and its preconditions, the upstream fix commits, vendor-recommended mitigations, and how confident it is in all of that. Four agents working from four slightly different readings of the advisory would produce four reports that don't merge.

Then three agents run in parallel, and a fourth runs after them:

| Agent | The question it answers |
|---|---|
| Exposure mapper | Does each target run the affected version, can an attacker reach the vulnerable path, and is anyone trying? |
| Mitigation engineer | What can we change without a patched build that measurably closes the hole, and what does it break? |
| Patch builder | Where does the fixed version come from for each target, and do we have a build that provably contains it? |
| Rollout planner | What exact sequence takes all of that to production, how do we know each step worked, and how do we undo it? |

The dispatch prompt for each one is short on purpose. It points the agent at the files instead of retyping them:

```text
Response <id>, workspace <dir>. Read ~/.claude/skills/security-response/briefs/_common.md,
then ~/.claude/skills/security-response/briefs/<brief>.md, and follow both.
Scope: <the targets and components in play, plus anything already known or ruled out>.
```

Everything ends up in a `SECURITY_RESPONSE.md` with one row per target and a go/no-go for each, plus one overall line. "Go" means the mitigation or patch is verified and the plan has a rollback. Platforms move independently, too: a shared server can be waiting on its vendor's packages while a container image is already rebuilt, so the report has to say who each target is waiting on.

## The inventory is a baseline, not the truth

The skill ships with an inventory of the estate: the big sites with dedicated hosting, the shared servers, how each CMS gets updated, which base branch each repository deploys from. It can't be the source of truth, though. Between new projects, hosting moves, and sites that get handed over or retired, what we're responsible for as a company changes faster than any document gets updated.

So the skill treats our GitHub organization as the canonical list. Every response sweeps the non-archived repositories by dependency, searching lockfiles, Dockerfiles, and CMS version files with [`gh search code`](https://cli.github.com/manual/gh_search_code), rather than relying on what anyone remembers. When a hit turns up in a repository the inventory doesn't place, the agent works out the platform from the repository itself: a deploy workflow that copies files to a server, a `vercel.json`, a Railway [`.railway/railway.ts`](https://docs.railway.com/infrastructure-as-code), an image-push step. Anything it can't resolve gets reported as "hosting unknown", never dropped.

That paid off on the first run. The PHP sweep turned up two containers the inventory hadn't caught up with yet, both of which needed the update, along with about a dozen repositories whose hosting wasn't written down anywhere the skill could find it.

## Every claim says how it knows

The rule I'd carry into any multi-agent workflow: every claim is labeled with its basis.

- **Verified:** the command and its output are saved in the workspace.
- **Read:** it came from a file, a vendor page, or a read-only live query, and the source is cited.
- **Assumed:** and the claim says why.

The risk table carries those labels cell by cell, and a target whose exposure is entirely assumed isn't reported as safe. It's reported as unknown. A confident guess is worse than a marked gap, because the merge step can't tell it apart from a fact. When the orchestrator reads an agent's findings, the first thing it checks is anything marked verified without saved evidence.

## Prove it in a container

The mitigation engineer derives candidates from the upstream fix itself, not from whatever list is circulating online, and proves each one in a throwaway container with three tests: the vulnerable behavior reproduces on the unpatched version, the same input no longer reaches the bug with the mitigation on, and the traffic the business actually depends on, such as real file uploads, still works.

The report also has a "Doesn't help" section, and it's as valuable as the list of mitigations that do. For the PHP bugs, a few commonly suggested ideas didn't hold up. You can't turn off upload progress tracking with `ini_set()` from application code, because the setting can't be changed at runtime and the call returns `false`. Lowering `max_file_uploads` doesn't bound the relevant input. Resource limits on the worker process make things worse, not better. Each of those has a test or a citation behind it.

When the agent can't build a safe reproduction, it says so. For the PHP bugs, it couldn't drive the affected build into the failure within the default limits, so the evidence is a proxy, showing that the hostile request shape reaches the vulnerable parser, and it's labeled as a proxy.

One practical lesson here cost me a frozen laptop. On the first run, two agents ran unbounded x86 containers at the same time, a PHP source build plus a test, under emulation on an ARM Mac. They took about 960% CPU and locked up my browser, terminal, and IDE. The shared brief now caps every container's CPU and memory, fixes compile parallelism at three jobs instead of the core count, allows one build at a time per agent, and prefers ARM images unless fidelity to the production build demands otherwise.

## Nothing live without asking

This is the part the skill exists for. Nothing changes staging or production, a live policy, a registry, a remote branch, or a server until I approve that specific step. Approval doesn't carry over from staging to production, from one target to the next, or from "go ahead with the plan" to an individual command. In practice it's a handoff: when the plan reaches a live step, the agent gives me the exact command, what it should change, and how to roll it back, and I review it and run it myself once I'm satisfied.

Subagents hold no approvals at all. They can read live state freely, including cluster state, logs, error tracking, and policy descriptions, but when a step needs a write, they write down the exact command for the rollout plan and stop.

Instructions are only half of that, so there's a backstop: a [`PreToolUse` hook](https://code.claude.com/docs/en/hooks) that inspects every shell command and certain MCP tool calls before they run. If one looks like it could change live infrastructure, such as `kubectl apply`, `gcloud … update`, `ssh`, a `git push`, a registry push, a Railway deploy, or an HTTP write to anything that isn't localhost, the hook returns an "ask" decision. That forces a permission prompt whatever mode the session is in, and the hook logs the attempt.

```json
{
    "matcher": "Bash|mcp__railway__.*|mcp__plugin_sentry_sentry__update_.*",
    "hooks": [
        {
            "type": "command",
            "command": "python3 -I ~/.claude/skills/security-response/bin/live-guard.py",
            "timeout": 10
        }
    ]
}
```

It never denies anything, and its patterns are deliberately biased toward asking. Reading the log, a fair share of what it catches is harmless, such as a local commit whose message happens to mention an infrastructure script by name. A false positive costs one prompt. A false negative costs a production change nobody approved.

The hook started out registered in the skill's own frontmatter. A test showed it never fired inside subagents, which is where it's needed most, so it moved to my global settings. I confirmed the fix by having a subagent run a harmless command that matches one of its patterns and watching for the prompt. Even so, the skill treats the hook as a backstop: the orchestrator stops before every live step whether the hook fires or not.

## Servers go through me

Some targets can't be reached from my machine, or shouldn't be reached by an agent. For those, agents write read-only collection scripts: no writes, no restarts, safe to run as root, output to stdout. The orchestrator bundles each server's scripts into one file, so it's one run per server, and gives me a single command that pipes the script over SSH and saves the output as evidence.

Writing scripts that run correctly on someone else's server is a skill of its own, and the brief has collected a list of mistakes that each cost a re-run:

- Older CentOS servers have no `python3`, so the scripts use Perl or shell.
- `dpkg-query -W` also lists removed packages that left their configuration behind, and the orchestrator once misread one as installed. The scripts now always print the package status.
- An unbounded `grep` across every docroot on a shared server ran for over twenty minutes before we killed it.
- A suspended site, or one whose DNS has moved, can still answer on the server's IP, so reachability is checked with `curl --resolve` rather than DNS.

## Two runs so far

**The PHP replay.** We had already responded to the PHP advisories a week earlier, so the first run was a validation: replay the response against today's estate, and see whether the skill reaches the same conclusions and anything we missed. It confirmed the fixed builds and restarted workers on every server it could check, confirmed the mitigations were in place where we expected them, and picked up the two containers and the unmapped repositories. It also exposed a gap in the orchestration: the exposure mapper reported new targets, but the orchestrator never passed them to the mitigation and patch agents, so it ended up doing their work itself. Forwarding new targets to the other agents is now a required step.

**The Symfony releases.** Today Symfony shipped [security releases](https://symfony.com/blog/category/releases) across all four maintained branches. Every deployed application we host that uses Symfony was behind. Seven were updated and released the same day, each through its normal path: development branch, green CI, then production, with every merge and push approved one at a time. One application is pinned to a framework version that can't take the upstream release, so it got the fix backported as a [Composer patch](https://github.com/cweagans/composer-patches), and its CI needed two fixes of its own because its base image has reached end of life. An application scheduled for decommission got its remaining advisories ignored explicitly, each one naming its package and fixed version so the decision is visible later. And a CMS that bundles an unmaintained Symfony version was recorded as something only a CMS release can fix.

## It gets better every time

The last step of every response is a close-out that updates the skill itself. The inventory picks up whatever the run proved stale or newly mapped. The orchestration and the briefs pick up the lessons, and each lesson is written with its date and the reason behind it: "on 2026-10-27, this step was skipped and the orchestrator had to do the patch builder's work itself" is far more persuasive to a future session than a bare "always do X." When a project's own documentation should learn something, the skill proposes the change instead of writing it into the repository quietly.

If you're building something similar, that's my advice. Let the agents do the reading, because they're tireless at sweeping repositories, lockfiles, logs, and vendor changelogs. Make them say how they know what they claim to know. Prove the fix in a container before believing it. And keep every write to a live system behind a human decision, with a hook behind the instructions in case the instructions aren't enough.
